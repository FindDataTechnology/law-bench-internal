# 设计：域智能体团队

## 1. 一句话

把已经在库里长出来的四个接口（`authoring_tasks` 派单、`domain_proposals` 提案评审、`authoring_events` 审计、`estate.matrix` 缺口）接上七个岗位，并用**闸门**而不是**自主性**来保证质量。团队的地基不是"更聪明的提示词"，是"每个错误都在落库前被机器抓住，抓不住的升级给人"。

## 2. 为什么是这七个岗位

岗位不是按职能分的，是按**这个库已有的动词**分的。每个岗位只做一件事，且它做的事已经有一个现成的内核入口：

| 岗位 | 消费 | 产出 | 依赖的内核入口 |
|---|---|---|---|
| 取材员 | 语料目录、域订阅范围 | 取入的文档/条款 + 覆盖计数 | `corpus_catalog.adopt_*` |
| 结构员 | 已取入文档、模板词表 | 实体/关系单位（逐字依据） | `authoring_create_unit(s)` |
| 概念员 | 判例/说理语料 | **提案**（带逐字 quote） | `extraction.run` → `proposals.submit` |
| 质检员 | 产物 + 语料 + 本体快照（**不含起草思路**） | 复核结论 + 阻断理由 | 只读 |
| 评测员 | 域标准、评测集 | rubric 归属、评测运行、判官实探 | `domain_rubrics`、`lane.probe` |
| 发布员 | 已发布快照 | 版本 + 消费者足迹 + digest 双侧对照 | `distribution.publish` |
| 巡检员 | estate 矩阵、台账 | 缺口任务、悬空清单、漂移报告 | `dispatch` |

值班长（`lead`）不在表里：它是唯一持 `confirm` 的人。

## 3. 闸门分级：G0 到 G3

```
G0 机器判定（确定性）      逐字引文存在、键形状、词表内、端点闭合、幂等、计数
   │  ↓ 通过
G1 独立复算（另一进程）    同一条主张从库里重算一遍，必须相等
   │  ↓ 通过
G2 人的决定（lead）        确认提案、发布、归档、放宽范围
   │  ↓ 通过
G3 平台策略（admin）       模板版本、开新域、登记新库
```

智能体只能在 G0、G1 内闭环；G2/G3 永不由智能体触发。这条分界不是保守，是发布契约的要求：`ontology_publications` 不可改写、digest 双侧对照意味着"发布出去的快照可被消费方无条件信任"——一旦机器能签字，这条承诺就变成"机器说它没问题"。

## 4. 事实 / 判断的分界（本 change 的核心判断）

```
事实类（可闭环）                        判断类（只提案）
──────────────────────────────────     ──────────────────────────────
文档标题、条款号、条文正文               概念边界（两个说法是不是一个概念）
发文机关、文种、日期                     引文是否"支持"这个结论
块数、覆盖度、接地计数                   某个标准够不够格
键的归名结果（规则在 pack 里）          两个单位是否近重复（要人判）
```

为什么这条线可靠：事实类的正确答案**已经逐字写在库里**，读出来不需要模型（上一轮 1,208 条民法典条款就是这么来的，零幻觉风险）；判断类没有客观答案，模型只能给候选。

## 5. 身份与审计

- 智能体是域成员：`agent:<role>@<domain>`，`domain_members.role = expert`，**不带 `admin`/`*`**。
- 事件里 `operator` 记 `agent:<role>@<domain>`，发布快照可审计"这条是机器写的还是人写的"。
- 提案 `source` 记 `agent:<role>@<domain>`，与舰队的 `fleet:<id>/<post>` 并存。

**已核实的机制（读代码确认，不是设想）**：`verify_key` 返回 `{"sub": user_id, "name": "", "email": "", "scopes": [...]}`
（`src/web/auth/apikey.py:150`），也就是说**身份就是 `api_keys.user_id`，权限就是那一行的 `scopes`**。
所以"智能体不是管理员"是可以在铸凭据时物理保证的，不需要靠约定。三处闸点：

| 闸点 | 位置 | 现状 | 要加什么 |
|---|---|---|---|
| 铸凭据 | `apikey.create_key`（`apikey.py:99`） | 接受任意 `user_id` + `scopes` | `user_id` 以 `agent:` 开头且 `scopes` 含 `admin`/`*` → 拒 |
| 确认提案 | `proposals.confirm`（`proposals.py:429`） | 只在 `submitted_by == actor and not admin_override` 时拒 | `submitted_by` 以 `agent:` 开头 → 无论 `admin_override` 一律 403 |
| 域角色 | `domain_members`（`role='expert'`） | 按 `user_id` 判定 | 无改动；智能体就是一普通成员 |

**这条口子是实打实的**：路由两处都把 `admin_override=is_platform_admin(user)` 直接传下去
（`console.py:248` 批量确认、`console.py:1049` 单条确认），而 `is_platform_admin` 只看 `admin`/`*` scope。
所以一个带 admin scope 的智能体身份，确认自己提交的提案会成功，只在 `decision_note` 里留一句
`[admin-override]`。这不是"可能"，是当前代码的确定行为。

审计的另一半：智能体**不需要** Logto 用户——API key 通道的 `sub` 就是 `api_keys.user_id`，
所以登记一个 `agent:concept@legal` 只需两行数据（key 一行、成员一行），不需要改 IdP。

## 6. 跨生产者去重（现状是漏洞）

现在的唯一索引是 `(domain_id, source, external_key) WHERE state='pending'`。舰队岗 + 应用内团队同时上线后，同一主张会变成两行。

```
提议的去重身份            (domain, 规范化 external_key)  + source[] 列表
迁移既有 pending 行       同键合并，保留最老一行，其余 source 并入列表
证据不同怎么办            同一键但 digest 不同 → 保留两行并标"证据冲突"，交人判
```

第三条重要：**不能因为键相同就把两份不同依据合并掉**——冲突本身是信息。

## 7. 运行台账

```
run: { id, role, domain_key, task_id?, started_at, ended_at,
       outcome: ok|thin|failed|stopped, input_digest,
       counts: {produced, submitted, skipped{...}}, model?, tokens?,
       artifact_refs: [proposal_batch | task_ids | report] }
```

四态的含义与动作：

| 结局 | 含义 | 动作 |
|---|---|---|
| `ok` | 产出可用 | 进评审 |
| `thin` | 有产出但薄（可用率低于阈值） | **升级给人，不重跑** |
| `failed` | 前提缺失/闸门拒绝 | 报告拒绝原话，**不重试** |
| `stopped` | 不变量触发（批次不收敛等） | 报告停止原因，等人处置 |

只有"读类失败且无副作用"允许自动重试。这条来自实测教训：两次批次永不收敛、一次键未归名，如果当时允许重试，只会把错误放大。

## 8. 评审保持亚线性的三件事

1. **按批决策**，不按条：一批一个共同主张 + 差异清单。
2. **提案方必须交批摘要**：共同主张、与现有单位的冲突、自己没把握的项。没有摘要的批次不受理。
3. **机器先拿掉不值得看的**：键已在库（实测 3/48）、引文不逐字、端点不闭合——这些不占人眼。

## 9. 产品面：值班长的一天（15 分钟）

```
┌─ /d/{key}/team ───────────────────────────────────────────────┐
│ 质量比   接地 40% · 证据 45% · 参照 100% · 覆盖 1.7% · 时滞 4.0h │
│ 待确认   3 批 / 48 条   [批 1: 15 条 · 共同主张: 抽取自 statutes] │
│          [批 1 里 2 条键已在库 → 已由质检标注为冗余]             │
│ 运行记录  昨日 6 轮: 4 ok / 1 thin / 0 failed / 1 stopped        │
└───────────────────────────────────────────────────────────────┘
   点进一批 → 差异清单 + 3 条抽样引文（页面现场回源高亮）→ 确认/整批退回
```

页面不提供"一键全绿"，也不提供"全部确认"。

## 10. 分期

| 阶段 | 内容 | 判据 |
|---|---|---|
| 1 | 巡检员 + 质检员（只读）+ 运行台账 | `tasks` 从 0 变成有内容；报告里每个数字都能被另一条 SQL 复算 |
| 2 | 取材员 + 结构员（确定性写） | 同输入重跑两遍，单位数完全一致 |
| 3 | 概念员（只提案）+ 批摘要 | 复核时滞不上升 |
| 4 | 评测员 + 发布员 | 判官实探不过不报分；digest 不一致即失败 |

## 11. 不做

- 不做"全自动确认"：发布承诺要求人签字。
- 不做按域 key 分支的编排：岗位参数进 pack。
- 不做智能体自评质量：六个比率全部从库里反算。
- 不做"重试到绿"：四态结局里只有一类允许重试。
