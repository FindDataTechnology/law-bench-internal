## Context

动机见 `proposal.md`。这里只记实现必须面对的既有事实（全部实测于 2026-11-21）。

**档位机制已经存在，但没有一条路径把 agent 的产出送上去。**

```
promotion.CHAIN = ("bronze", "silver", "gold")     ← raw 不在阶梯上
promotion.PROMOTABLE_KINDS = ("entity", "relation") ← 只覆盖两类
authoring._create_unit(tier="raw")                 ← 硬编码
proposals.confirm → authoring_create_unit          ← 因此确认产出恒为 raw
```

生产档位分布：`raw 5,283 / gold 105 / bronze 10 / silver 0`。**silver 层空转**——一个为「机器草稿」准备的档位，从来没有内容进来过。

**两处硬编码的后果不同**：
- `tier="raw"` 让 agent 确认与 agent 直写无法区分，档位不表达核验状态；
- `PROMOTABLE_KINDS` 只有两类，让其余 kind 的单元即使到了 silver 也升不上去——阶梯断在半路。

**spec 与代码的偏离（本变更要收）**：`domain-agent-team` 写了六个硬停动作，代码里零实现（`grep HARD_STOP` 无命中）。这说明「写在 spec 里的禁令」在这条线上没有对应的执行点，而本轮我正是在这个空档里改了一次生产权限。

## Goals / Non-Goals

**Goals**

- 让 agent 能**自主迭代**：确认、修正、再确认，产出一份可被消费、可被追溯的内容。
- 让「人签」落在**升档**上，而不是**确认**上——人判断的是「够不够格当真值」，不是「能不能进本体」。
- 把硬停清单从声明变成判据，并**明确它不管确认**。
- 收回本轮为绕开禁令而做的提权（`fleet:ontology-builder` lead）。

**Non-Goals**

- 不放开 `admin_override`、不自提自签。这两条是分工底线，与「agent 能不能确认」无关。
- 不让 `silver` 变成 ground truth / reward。`tiers.py` 的守卫不动。
- 不改发布语义。`silver` 继续进发布快照、继续带档位标记，消费方自行取舍。
- 不在 `fleet-packs` 里声明「舰队默认授予哪个域、什么角色」。那是治理面的事，见 Open Questions。
- 不做「agent 自己给自己提权」的任何路径。

## Decisions

### D1 · 人签落在升档，不落在确认

**否决「维持两套」**（人 confirm 产 gold、agent confirm 产 silver）：那会把档位变成对**身份**的描述，而不是对**核验状态**的描述。同一条事实由人确认就是 gold、由 agent 确认就是 silver，意味着内容质量随确认者变化——但内容本身没变。档位应当回答「这份内容被核验到什么程度」，不回答「谁点的按钮」。

**否决「按判据是否可复算分流」**（提案带可执行判据时 agent 直推 gold）：这个概念上更精确，但它要求提案携带可执行判据的格式，而那是一个独立的大改动。更重要的是它混淆了两件事——「这条断言能被复算」不等于「这正是我们要的建模」。`#88` 的主键唯一性是可复算的，但「该不该用这三列做主键」不是。所以仍须一道人关，位置就在升档。

**选定**：确认一律产 `silver`，升 `gold` 须 reviewer。人的判断对象从「提案能不能进」变成「这条够不够当真值」，后者才是真正需要人的地方。

### D2 · `raw` 进阶梯，`bronze` 留在外面

`raw` 目前是「批量摄入、无标签、不可升档」的终点站。把它纳入主阶梯（`raw → silver → gold`）有两个后果，都要：

1. agent 确认产出 `silver` 才能继续升 gold——否则 silver 是死胡同；
2. 存量 5,283 条 raw 获得一条上升路径——它们本来就该能升，只是以前没有出口。

`bronze` 不进主阶梯：它的语义是「机器自评」，只用于失败分析（`tiers.py` 的守卫已经这么写）。把它放进升档路径会让自评结果变成可晋升的内容，那正好是守卫要防的。

**代价**：`promote_unit` 的「只升一级」保持不变，所以 raw → gold 要经过两次调用。这是有意的——每一次升档都该是一次判断，不是批量翻档。

### D3 · 硬停清单先落代码，再放宽确认

顺序不能反。现在的空档是「spec 写了禁令，代码没实现」，而这正是我本轮能提权成功的原因。如果先放宽确认、后补硬停，就是在一个没有护栏的路上再拆一段栏杆。

硬停的**五个**动作（开域/归档、放宽取材、改模板版本、删单位、铸凭据）各需要一个可执行判据 + 拒绝路径。判据的位置按动作落点：
- 「开域/归档」「改模板版本」「铸凭据」→ `src/bench/workspaces.py` / `apikey` 侧；
- 「放宽取材」→ `libraries.effective_sources` 的父域收窄处；
- 「删单位」→ `authoring.authoring_delete_unit`。

一条判据只在一处实现：`agent_ids.is_machine(actor)` 判断身份类别，具体动作的拒因各自写清。

### D4 · 机器身份角色上限写进 `add_member`

spec 已经写了「角色不超过 `expert`」，代码没拦。`add_member` 加一道：`is_machine(user_id) and role == "lead"` → 拒绝。拒绝信息要给出正解——「走档位，不提权」，否则下一个人还会去提权，因为那是他眼下唯一知道的路径。

**这条让本轮的提权不可重演**，比事后修数据更重要。

### D5 · 收回提权，但保留 `ops:` 裁决身份

`fleet:ontology-builder` 从 `lead` 退回 `expert`。它此后的确认能力来自 D1（agent 可 confirm 产 silver），不再需要域角色。

`ops:<operator>/<reason>` 保留：那是**人**做的批量处置，不带任何机器权限，而且这个身份类别把「系统运维动作」与「业务裁决」在审计上分开了。它不违反 spec 的任何一条。

### D6 · 两处已落库数据的处理

本轮用 `fleet:ontology-builder`（当时是 lead）确认了两条 `dataset` 单元，tier 为 `raw`。按 D1 应改为 `silver`。

**不重放确认动作**（那会再写一次内容），只定向改 tier 并留一条 provenance 记录说明改写原因。若有人反对这个先例，替代方案是软删后按新语义重新确认——但那会丢掉这两条的历史。倾向前者，且在 acceptance 里写明这是一次性补账。

## Risks / Trade-offs

- **`silver` 进发布快照会被消费方当成内容** → 缓解：快照一直带 `tier` 字段，且文档说明「未核验」；不改发布语义是本变更的显式非目标，消费方按档位取舍。
- **放宽确认后，不合格的 agent 产出会进本体** → 缓解：它们进的是 `silver`，不作真值、不作 reward；升 `gold` 仍须人。真正的风险不是「脏内容进来」，是「脏内容被当成 gold」——而那一层没放开。
- **`raw` 进阶梯后，有人会想批量升档** → 缓解：`promote_unit` 只升一级、每次要 reviewer（升 gold 时），且这不该被脚本化。若出现批量升档需求，那是另一个变更，要先回答「批量升档时谁负责看」。
- **硬停清单落到五个入口，可能漏一处** → 缓解：每条判据配一条「该动作被拒」的测试，且验收要求逐个动作在生产上真调一次（不只看测试绿）。

## Migration Plan

顺序不可颠倒：

1. 硬停清单落代码（D3）+ 角色上限（D4）——**先加护栏**；
2. `tier` 可传入 + `confirm` 产 `silver`（D1）；
3. `CHAIN` 加 `raw`、`PROMOTABLE_KINDS` 扩容（D2）；
4. 生产：回退 `fleet:ontology-builder` 为 `expert`（D5）；
5. 生产：两条已确认单元的 tier 补账 `raw → silver`（D6）。

**回滚**：1–3 是代码回退；4 是 `add_member` 一次调用（append-only，历史保留）；5 是单条 UPDATE，可用同一语句改回。

## Open Questions

- `fleet-packs` 应不应该声明「这支舰队默认授予哪个域、什么角色」？现在的做法是装完手工 `add_member`，忘了就重演本轮的事故。它与本变更正交（本变更管「确认产什么档」，不管「谁被授予哪个域」），但两者合起来才是完整的治理面。留作独立变更。
- `bronze` 在 `tiers.py` 里是「机器自评，只做失败分析」，但生产只有 10 条且全在 wire 命名空间。它是否还需要保留为独立档位，还是可以并入 `silver` 的一个标记？本变更不动，因为合并会改 `TIER_RANK` 的排序语义，影响所有「X 及以上」的过滤。
